## 2. 背景与问题

项目已经具备 Chromium Trace 的安全导入、Worker 解析、事实聚合、证据引用、诊断规则和结果页，但当前体验更接近结构化诊断报告：

- 时间信息以卡片和列表字段呈现，没有统一可缩放时间轴。
- 网络、主线程、渲染、交互和帧不能在同一时间域内联动。
- 缺少 Flame Chart、Call Tree、Bottom-up 和 Event Log 等专家分析视图。
- 诊断虽然已有证据约束，但尚未形成完整的多因素竞争归因体系。
- Trace、HAR、NetLog 仍是独立分析，无法形成端到端证据路径。
- 大文件仍依赖全量 JSON 解析和对象传输，无法支撑长期扩展。

目标不是复刻整个 Chrome DevTools，而是建设一个离线性能分析工作台：保留 Chrome Performance 最有价值的离线分析闭环，并利用项目已有网络诊断资产形成跨源差异化。

### 2.1 实施基线与已有资产

实施必须以功能代码与设计文档已经汇合后的明确提交为基线，而不是分别从设计 worktree 或功能 worktree 推断整体完成度。开始阶段 0 前，应先合并目标功能分支、处理设计文档的未提交修订，并重新生成一次可追溯的能力基线。

本轮复核快照如下；这是 2026-08-01 的 Git 事实，不是永久分支承诺：

| 对象 | 复核 ref | 判定 |
|---|---|---|
| 设计 worktree | `80fd2d3` | 包含 V4 设计提交；当前文档另有未提交修订 |
| Trace 功能分支 | `ec6fc9a` | 包含 Batch 6 灰度分析、真实样本门禁机制与隐私导出 |
| 本地 `master` | `6d6dad8` | 已合并设计分支，但尚不能据此证明已合并 `ec6fc9a` |
| 共同实现基线 | `68d72ac` | 设计分支与功能分支在此之后分叉 |

阶段 0 的第一个动作不是开发 Timeline，而是产生一个“合流基线 ref”，并将该 ref 写入能力证据表、测试报告和 benchmark 产物。后续文档不得继续把 worktree 名称当作稳定架构边界。

目标分支已经具备以下资产，应复用和演进，不重复建设：

- Chromium Trace 安全导入、格式嗅探、gzip 支持和容量限制。
- `MinimalTraceAggregator` 的进程、线程、frame、导航和 Batch 3 事实采集。
- 网络、长任务、CPU Profile、里程碑、渲染、交互和 Forced Reflow 事实。
- 十三条证据约束诊断规则、确定性排序和主诊断筛选。
- 诊断证据过滤、隐私扫描和 Trace 白名单导出。
- 十七个合成 Golden Corpus 场景。
- 五个仓库外真实样本的可选注入门禁机制：目标分支中的 `src/benchmark/traceBatch6RealSamples.test.ts` 通过 `TRACE_SAMPLE_MANIFEST_PATH` 要求 `TRACE-SAMPLE-01` 至 `TRACE-SAMPLE-05` 位于 worktree 外，并检查能力、三次稳定性、容量和导出隐私。
- HAR 与 NetLog 的请求关联、保守时间对齐和证据融合。

同时，当前代码快照还证明了以下实施边界：

- `createFileParseInput`、`FileFormatRegistry` 与 `useAnalysisIntake` 已形成“预检推荐 -> 用户确认 -> parser 绑定 -> 严格校验 -> 解析”的可靠接入链路；Workbench 不得另建第二套文件识别入口。
- `AnalysisProgress` 已使用 bytes、events、requests、lines 或 rules 表示真实工作量，并通过 `taskId` 拒绝旧任务结果；Workbench 的建索引和查询进度必须复用这一语义，不得回到固定阶段百分比。
- `TraceResultPage` 当前仍是结论、概览、网络、主线程、渲染、交互和证据列表页；它是可用回退和聚合入口，不等于 Timeline Workbench 已实现。
- `TraceWorkerResponse` 当前返回完整 `TraceAnalysisResult`，还没有稳定 `sessionId`、查询 DTO、局部取消和按视口返回协议。
- `selectTraceDiagnoses` 当前按得分排序后选取第一个可作为主诊断的结果；这与第 10 节定义的症状驱动竞争归因仍有差距。
- Trace 能力仍受 `REACT_APP_ENABLE_TRACE_ANALYSIS` 控制。分阶段发布前不得删除该回退开关。

这里必须区分三种状态：

1. **门禁机制存在**：测试代码、五样本 manifest 契约和外部路径约束存在于目标分支。
2. **样本已提供**：当前验收环境实际配置了五个脱敏真实样本及 manifest。
3. **门禁已通过**：同一版本代码在指定环境中完成三次运行并保存了结果证据。

当前 Git 代码能直接证明第一项。2026-07-30 的既有运行记录表明样本已注入：`TRACE-SAMPLE-01/02/05` 通过，`TRACE-SAMPLE-03/04` 因 manifest 声明的多进程/OOPIF 能力与实际单 renderer 样本不符而失败。因此当前状态是“样本已提供、门禁未通过”，不是“未运行”，更不能写成“五个真实样本已经运行通过”。阶段 0 必须在合流基线 ref 上修正样本或 manifest 后重跑，并保存脱敏 artifact；旧分支的部分通过记录不能替代合流版本验收。

基线核验必须针对 Git 对象和明确 ref 执行：

- 使用 `git rev-parse` 固定当前 HEAD、目标分支和共同基线的提交 ID。
- 使用 `git ls-tree`、`git cat-file`、`git show <ref>:<path>` 或 `git grep <ref>` 检查目标分支内容。
- 使用 `git merge-base` 和双向提交差异确认分支祖先与分叉关系。
- 当前核验结果是：`ec6fc9a` 的父提交为 `68d72ac`；目标功能分支与设计分支已在共同基线后分叉，本地 `master` 合并了设计分支，但功能分支仍需单独核验和汇合。
- 不得只搜索当前检出目录后，就断言目标分支不存在某文件或能力。

当前仍有一个必须优先修复的基础问题：聚合器内部虽然支持周期性检查 `isCancelled`，但生产 Worker 当前传入恒定 `false`，因此现状只有终止 Worker 的外部取消，不是完整的协作式取消。

当前完成度不得用未经逐项验收的单一百分比描述。阶段 0 应按第 5 节计分项和第 6 节专家任务重新评估，并为每一分附上代码、测试或操作证据。

## 3. 产品边界

### 3.1 范围内

- 导入已有 Chromium Performance Trace。
- 展示 Trace 内已有的截图胶片、时间轴事件和指标。
- 网络、主线程、渲染、交互、帧、里程碑和 CPU Profile 分析。
- Summary、Flame Chart、Call Tree、Bottom-up、Event Log。
- 证据型诊断、竞争原因评估、限制说明和复测建议。
- Trace、HAR、NetLog 的时间校准、请求关联和证据合并。
- 本地离线处理、脱敏展示和白名单导出。
- 百万事件级解析、查询和交互优化。

### 3.2 明确排除

#### 录制

不通过 DevTools、CDP 或扩展控制浏览器开始、停止、重新加载录制，也不负责生成 Trace 文件。项目只分析已有文件。

#### 节流

不在采集时模拟慢速 CPU 或网络。离线分析可以识别 Trace 中已经发生的 CPU 或网络受限特征，但不能重放节流环境。

#### DOM 实时高亮

不在仍然运行的原网页上框选 LCP、CLS 或 Layout 对应 DOM 元素。离线文件没有可操作的原页面和 DOM 实例。

#### Heap Snapshot

不抓取或分析 JavaScript 堆对象图、对象保留链和完整内存泄漏。Trace 中已有的堆计数器、GC 和内存趋势仍可分析。

#### Paint Profiler

不重放单个 Paint 的底层绘制命令。Trace 中已有的 Paint 事件、耗时和关联帧仍可展示。

### 3.3 截图胶片边界

截图胶片属于离线分析范围，不属于本项目排除的录制能力：

- Chrome 录制阶段将 Screenshot 事件和图像写入 Trace。
- 本项目导入 Trace 后离线解析并展示已有截图。
- Trace 不包含截图时，不补生成历史画面。
- 胶片用于视觉上下文，不等价于视频、DOM 回放或操作重演。
- 截图不进入诊断 DTO、日志、持久化存储或默认导出。

### 3.4 从可靠接入到 Workbench 的用户流程

Workbench 是现有可靠接入链路的下游，不是新的上传器：

```text
选择文件
  -> 本地预检与格式推荐
  -> 用户确认 parser
  -> 专用校验与基础解析
  -> 提交可用的诊断结果
  -> 创建 Workbench 会话并建立最小索引
  -> 进入 Timeline；其余索引按需或后台构建
```

交互要求：

- 基础诊断结果提交后才允许显示 100%；Workbench 建索引是后续明确命名的任务，不得伪装成同一个长尾进度。
- 最小索引未就绪时，保留现有结果页可读，并在工作台入口显示“正在准备时间轴”，不清空稳定结果、不展示空画布。
- 同一文件不得为了进入 Workbench 再次读取或重新识别格式；会话必须绑定已确认的 `parserId`、文件指纹和任务 ID。
- 关闭文件、重新上传或 Worker 崩溃时，取消该会话的所有查询并释放截图 Blob URL、索引、字符串表和 Transferable。
- 页面刷新后不恢复原始文件或截图。产品不得声称自动保存；用户需要重新选择本地文件。

### 3.5 多源追加与会话边界

- 阶段 2 先交付单 Trace 会话；阶段 4 才开放向该会话追加 HAR、NetLog。
- 每次追加仍经过统一预检、确认、绑定和严格校验，不允许因当前会话是 Trace 就静默把未知 JSON 当作 NetLog 或 HAR。
- Source 面板显示每个来源的文件名脱敏摘要、解析状态、时间域状态、关联覆盖和移除操作。
- 移除某个来源只撤销依赖它的跨源关联与结论，不销毁其他来源的稳定结果。
- 同一来源重复追加时必须让用户选择“替换”或“取消”；首版不隐式合并两个同类型文件。
- 会话 ID、文件指纹和实体 ID 只在本地内存使用，不进入公开 URL、日志或默认导出。

| 能力域 | 分值 |
|---|---:|
| 时间轴与跨轨联动 | 20 |
| 主线程与 CPU 分析 | 15 |
| 网络瀑布 | 10 |
| 渲染、帧与交互 | 10 |
| Call Tree、Bottom-up、Event Log | 10 |

| 稳定性、隐私与离线能力 | 10 |
| 事件详情、搜索与过滤 | 5 |

核心 65% 的判定同时满足：

- 总分不低于 65。
- 时间轴、主线程、网络、交互和证据五项分别达到目标能力的 60%。
- 十二个专家任务全部闭环。
- 不能通过建设边缘能力弥补核心分析能力不足。
- 每项得分必须关联可复现的样本、测试或专家任务记录，禁止用主观估计替代验收。

差异化单独计分，不混入 Chrome 对标分：

| 差异化能力 | 分值 |
|---|---:|
| 跨源联合诊断 | 15 |
| 自动性能洞察 | 8 |
| 大 Trace 能力 | 7 |

### 5.1 能力证据表与计分规则

阶段 0 必须生成独立的能力证据表，每个计分项只允许以下状态：

| 状态 | 含义 | 是否计分 |
|---|---|---:|
| `implemented-verified` | 合流基线中存在实现，且对应自动化测试或专家任务已通过 | 是 |
| `implemented-unverified` | 存在实现，但缺少目标样本、浏览器交互或运行记录 | 否 |
| `partial` | 只能完成该能力的一部分，限制和缺失项已列明 | 按冻结的子项计分 |
| `designed` | 只有设计、接口草案或 Spike 结论 | 否 |
| `absent` | 未实现 | 否 |

每条记录至少包含：能力 ID、用户可观察行为、代码 ref、测试或任务证据、样本 ID、限制、复核人和复核日期。汇总分必须由记录自动计算，不允许手工填写总百分比。设计稿中的“核心 65%”“长期 85%”都是目标标签，不是当前完成度。

## 6. 核心专家任务

阶段验收使用固定任务集：

1. 从慢交互定位输入延迟、处理耗时和呈现延迟。
2. 从长任务定位主要调用链和 self time 热点。
3. 判断 LCP 延迟来自资源发现、网络、主线程还是渲染。
4. 判断请求延迟来自排队、连接、TTFB、下载还是主线程派发。
5. 定位掉帧或超预算帧对应的脚本和渲染活动。
6. 定位 Forced Reflow 与关联任务。
7. 识别布局偏移、动画和视觉变化。
8. 判断第三方脚本或浏览器扩展是否贡献主要耗时。
9. 判断是否呈现 CPU 受限、GC 压力或内存增长特征。
10. 在选定时间范围内查看 Call Tree、Bottom-up 和 Event Log。
11. 将 Trace 请求与 HAR、NetLog 请求关联并解释冲突。
12. 从诊断结论跳转到时间范围、事件、调用栈和原始证据。

每个专家任务必须固化为一份任务卡，包含：输入样本、起始界面、允许操作、期望事实、允许的结论等级、必须展示的限制、成功路径和最大交互步数。验收记录同时保存结论正确性与用户路径；不能只证明底层函数返回了数据，就视为专家任务闭环。

## 7. 总体技术方案

### 7.1 架构原则

- 核心解析、查询、聚合和诊断继续在 Web Worker 中执行。
- UI 不接收完整 Trace 原始事件数组。
- 解析引擎、统一数据模型、查询协议和 UI 相互隔离。
- 时间轴渲染数据与诊断事实数据分离，但通过稳定 ID 关联。
- 所有结论必须能够回溯到事实和证据。
- 缺失上下文、时间未校准和弱关联必须显式降级。

### 7.2 分层架构

```text
Trace / HAR / NetLog
        |
        v
Input Registry + Safety Limits
        |
        v
Analysis Engine Adapter
        |
        +-- Existing Minimal Aggregator
        +-- Chrome Trace Engine candidate
        +-- Perfetto Trace Processor candidate
        |
        v
Unified Analysis Core in Worker
        |
        +-- Timeline Columnar Store
        +-- Raw Evidence Store
        +-- Time and Entity Indexes
        +-- Cross-source Correlator
        +-- Diagnosis Engine
        |
        v
Worker Query Protocol
        |
        v
React Performance Workbench
```

报告数据与 Workbench 数据必须分离：

- `TraceAnalysisResult` 继续服务现有结论和聚合列表，作为稳定回退。
- `WorkbenchSessionDescriptor` 只向 UI 暴露会话 ID、来源摘要、能力声明、时间范围、轨道摘要和限制。
- 大规模时间轴列、原始事件、调用栈详情和截图保留在 Worker 会话内，通过查询协议按需取得。
- 两类 DTO 通过稳定 fact/evidence/entity ID 互相跳转，不允许 UI 从报告 DTO 反向拼装时间轴。

Workbench 会话至少包含以下生命周期：

```text
creating -> indexing-minimum -> ready -> enriching
                    |             |
                    v             v
                 failed       degraded
                    \             /
                     -> releasing -> released
```

`ready` 表示最小可交互时间轴已可用；`enriching` 表示 CPU 聚合、截图解码或跨源索引仍在后台准备。局部能力失败进入 `degraded`，不能把整个会话误报为解析失败。

### 7.3 引擎适配

引擎适配分两步完成：

1. 阶段 0 先通过 Spike 验证现有聚合器、Chrome Trace Engine 和 Perfetto Trace Processor 的能力与约束，冻结最小接口契约。
2. 阶段 1 再实现适配层。不得先按某个候选引擎的 API 设计生产接口，再倒逼其他实现适配。

`TraceEngineAdapter` 的能力至少覆盖：

- 文件或事件流摄入。
- 元数据、进程、线程和导航解析。
- 时间轴事件查询。
- CPU Profile 与调用栈查询。
- 网络、渲染、交互、帧和截图查询。
- 原始证据按 ID 查询。
- 能力声明和缺失原因。
- 进度、取消和错误协议。

现有 `MinimalTraceAggregator` 保留为基线实现。Chrome Trace Engine 和 Perfetto Trace Processor 必须先通过隔离 Spike，对格式覆盖、包体、浏览器兼容、隐私、性能和 API 稳定性做决策记录，未经决策不得直接成为生产依赖。

### 7.4 数据布局

高频、大规模时间轴数据优先采用列式布局，但不要求所有数据机械地改成 TypedArray：

- 时间戳、持续时间、轨道 ID、父 ID、事件类型使用 TypedArray。
- 名称、分类、URL 片段和函数名使用去重字符串表。
- Worker 与 UI 之间使用 Transferable 传递绘制批次。
- 原始 args、截图和调用栈详情保留在 Worker 或会话内存中。
- UI 按视口、选区或事件 ID 查询所需数据。
- 低频配置、能力声明、限制和详情 DTO 保持可读对象结构。
- 是否列式化由 10 万、50 万和 100 万事件基准决定，不以“全部 TypedArray”作为架构目标。

### 7.5 索引

- 按开始时间排序的事件列，以及结束时间或最大结束时间辅助信息。
- 分层时间桶、区间树或等价的重叠查询索引，用于视口查询。
- 父子事件和发起关系索引。
- Profile node、sample 和 stack 索引。
- 请求 ID、导航、frame、process、thread 索引。
- 跨源实体索引和匹配候选索引。

索引必须返回所有与 `[startUs, endUs]` 相交的事件，不能只按事件开始时间过滤，否则会漏掉开始于视口外、持续到视口内的长事件。禁止每次缩放、悬浮或选区变化时扫描全部事件。

### 7.6 Worker 查询协议

查询协议使用版本化、可判别联合类型，禁止使用无约束的 `data: unknown`：

- 每个分析会话拥有稳定 `sessionId`。
- 每次查询拥有独立 `requestId`，响应必须回传同一 ID。
- 每个响应同时回传 `sessionRevision`；UI 丢弃旧会话或旧 revision 的迟到响应。
- 视口、选区、事件详情、CPU 聚合、截图和证据查询分别定义明确的请求与响应 DTO。
- 查询响应声明 schema version、能力缺失和截断信息。
- 视口与列表查询必须有明确上限、排序键和续页或细化策略，禁止用未声明的静默截断保护 UI。
- `cancel-query` 只取消目标查询，不破坏同会话其他稳定结果。
- 关闭文件、上传新文件和 Worker 失败必须释放整个会话资源。
- 客户端实现超时、过期响应丢弃和显式错误分类。
- 生产 Worker 必须把真实取消状态传入读取、聚合、索引构建和长查询。

查询错误至少区分：`unsupported-capability`、`invalid-range`、`query-cancelled`、`query-timeout`、`result-truncated`、`session-released` 和 `worker-failed`。取消是正常控制流；可恢复查询错误只影响对应轨道或抽屉，不清空当前稳定画面。

### 7.7 大 Trace 预算与背压

“100 万事件”不能单独代表输入规模。所有基准和限制同时记录：

- `sourceBytes`：原始文件或 gzip 大小。
- `jsonBytes`：解压后的 JSON 字节数。
- `eventCount`：事件数及主要事件族分布。
- `screenshotEncodedBytes` 与 `screenshotDecodedBytes`。
- Worker 峰值内存、UI 峰值内存和单次传输字节数。

当前 128 MiB JSON 安全限制不得为了追求事件数而静默提高。阶段 0 需要用样本矩阵决定继续全量 `JSON.parse`、引入增量解析，或明确保持安全上限；任何变化都必须有浏览器兼容、OOM 行为和取消响应证据。

Worker 查询采用 latest-wins 或显式取消处理高频视口变化；并发查询数、返回批次大小和详情缓存上限由 benchmark 冻结。发生背压时优先丢弃过期查询，不降低当前稳定视图的证据完整性。

## 8. 统一时间与实体模型

### 8.1 时间域

所有时间保留原始来源和校准状态：

```ts
interface TimeDomainRef {
  source: 'trace' | 'har' | 'netlog';
  domain: string;
  calibrated: boolean;
  offsetUs?: number;
  uncertaintyUs?: number;
  evidenceIds: string[];
}
```

只有校准完成且不确定性处于阈值内时，才允许生成跨源端到端时间结论。

### 8.2 时间轴模型

```ts
interface TimelineEventRef {
  id: string;
  trackId: string;
  startUs: number;
  durationUs: number;
  depth: number;
  category: string;
  parentId?: string;
  initiatorId?: string;
  entityIds: string[];
  evidenceIds: string[];
  detailRef?: string;
}
```

轨道通过 `TrackDefinition` 注册，核心画布不感知具体业务类型。

### 8.3 原始证据

- `evidenceId` 稳定映射到原始事件索引或受控详情。
- 默认只返回轻量引用。
- 详情按需查询，并通过白名单投影返回。
- 原始事件不得直接进入诊断、日志或导出。

## 9. 截图胶片

### 9.1 数据处理

- 识别 Chromium Trace 中的 Screenshot 类事件。
- 提取时间戳和图像数据，不纳入普通 evidence DTO。
- 对图像数量、单图大小、总解码内存设限。
- 按时间和内容哈希去重。
- 使用 Blob URL 按需解码，离开会话时统一 revoke。

### 9.2 交互

- 在概览区域提供 Filmstrip 轨道；出于屏幕内容隐私，首次进入会话时默认折叠，用户主动展开后才解码和显示缩略图。
- 悬浮时间轴时显示最近截图。
- 点击截图打开大图。
- 截图、时间游标、选区、Interaction 和 Frame 使用同一时间坐标。
- 文件没有截图时展示“录制文件未包含截图数据”，不显示空轨。
- 截图缩略图不能成为唯一交互入口；键盘用户可按时间顺序聚焦截图，并读取“录制截图，时间 1.25 秒”等不推测画面内容的标签。

### 9.3 隐私

- 不持久化到 localStorage 或 IndexedDB。
- 不上传、不 OCR、不自动分析图片内容。
- 不进入诊断报告和默认导出。
- 提供隐藏轨道和释放截图内存操作。
- 大图查看器关闭后将焦点返回触发截图；离开会话或执行“释放截图内存”后，已生成的 Blob URL 必须全部失效。

## 10. 诊断引擎

### 10.1 目标

时间轴回答“发生了什么”，诊断引擎回答：

- 哪些现象影响用户体验。
- 哪些候选原因与现象相关。
- 证据和反证分别是什么。
- 归因可信到什么程度。
- 还缺什么信息。
- 如何复测和验证。

### 10.2 处理流程

```text
结构化事实
  -> 指标和基线
  -> 候选原因
  -> 必要证据、支持证据和反证
  -> 多原因竞争评分
  -> 证据型结论
```

### 10.3 首批诊断域

#### 浏览器扩展或插件影响

证据：

- 扩展 scheme、脚本栈、进程或线程。
- 扩展任务 CPU 占比。
- 与慢交互、LCP、长任务的时间重叠。

允许输出“扩展活动与问题高度相关”。仅检测到扩展存在时不得输出影响结论。扩展 ID 默认脱敏。

#### 设备 CPU 性能约束

证据：

- 主线程和总体 CPU 持续忙碌。
- 同类任务整体拉长。
- 多线程饱和、设备元数据、采样信息和对照基线。

单份 Trace 通常只能输出“呈现 CPU 受限特征”，不能直接证明设备性能差。必须列出工作量、扩展、后台活动和节流等替代解释。

#### 内存和 GC 压力

证据：

- 堆趋势、GC 频率和暂停。
- 分配计数器。
- GC 与交互或长任务重叠。

没有 Heap Snapshot 时，不得输出对象保留链或确定内存泄漏。

#### 网络瓶颈

Trace 支持：

- 请求发现、排队、优先级、TTFB、下载、缓存和失败。
- 主线程派发等待。

HAR 和 NetLog 增强：

- DNS、TCP、TLS、Socket 排队、连接复用、代理、重试和协议。

#### 主线程和脚本

- 长任务、self time、total time。
- CPU Profile、调用树、第三方占比。
- 与交互、渲染和网络回调的关联。

#### 渲染和视觉稳定性

- Style、Layout、Paint、Composite。
- Forced Reflow、Frames、CLS、动画合成状态。
- 截图用于视觉上下文，但不作为 DOM 事实。

#### 服务端和传输

- Server-Timing、HAR timing、NetLog Socket 和 Trace 请求。
- 缺少服务端证据时，只能定位“等待阶段”，不能推断内部服务根因。

### 10.4 结论结构

```ts
interface DiagnosisFinding {
  id: string;
  domain: string;
  phenomenon: string;
  impact: string;
  attributionLevel:
    | 'confirmed'
    | 'highly-correlated'
    | 'possible-contributor'
    | 'observation'
    | 'insufficient';
  evidenceConfidence: 'high' | 'medium' | 'low' | 'insufficient';
  evidenceIds: string[];
  counterEvidenceIds: string[];
  competingCauses: Array<{
    findingId: string;
    relationship: 'alternative' | 'contributor' | 'downstream-effect';
    reason: string;
  }>;
  limitations: string[];
  verificationSteps: string[];
  advice: string[];
  timeRange?: { startUs: number; endUs: number };
  entityIds: string[];
}
```

### 10.5 技术策略

- 确定性规则负责事实判定和基础归因。
- 版本化阈值负责可回归的严重性评价。
- 同 Trace 空闲区间、同场景多份 Trace 和设备分组提供统计基线。
- `evidenceConfidence` 表示证据可靠程度，`attributionLevel` 表示因果强度；两者不得混用。
- 先建立慢交互、LCP 延迟、掉帧等症状实体，再将候选原因关联到症状，不能仅按时间范围对规则结果分组。
- 每个候选原因必须声明必要证据、支持证据、反证、阶段覆盖率和替代解释。
- 时间重叠只证明相关，不能单独将归因升级为 `confirmed`。
- `confirmed` 只用于存在直接因果链且替代解释被有效排除的情况；普通重叠最高只能是 `highly-correlated` 或 `possible-contributor`。
- 禁止第一条命中规则或最高分规则自动成为主因。
- 大模型不是必需组件，不读取原始敏感 Trace，不生成归因事实。
- 如未来接入 LLM，只允许改写白名单诊断 DTO。

### 10.6 诊断域的结论边界

- 扩展影响：可以依据扩展 scheme、脚本栈、进程、CPU 占比和症状重叠判断相关性；仅检测到扩展存在时不得输出影响结论，也不得依赖无法从离线 Trace 可靠还原的“扩展注入 DOM 操作”。
- 设备 CPU：只输出“CPU 受限特征”，不输出“设备性能差”或“检测到 CPU 降频”，除非输入包含经过验证的硬件频率证据和对照基线。
- 内存与 GC：只判断堆趋势、GC 频率、暂停及其症状贡献；没有 Heap Snapshot 时不得判断对象保留链或确定内存泄漏。
- 服务端与传输：Trace 可定位等待阶段，DNS、TCP、TLS、Socket 和服务端归因必须由 HAR、NetLog 或 Server-Timing 等跨源证据支持。

## 11. 跨源联合诊断

### 11.1 匹配层级

1. 直接 ID 或明确上下文字段。
2. 导航、URL 脱敏键、方法和时间窗口的组合匹配。
3. 时间近邻和阶段特征的候选匹配。

### 11.2 置信度

- `high`：可用于端到端归因。
- `medium`：可显示关联，但结论必须包含限制。
- `low`：只显示候选，不合并因果链。
- `conflict`：展示冲突字段，不自动选择来源。

### 11.3 证据图

支持以下路径：

```text
Navigation
  -> Trace Resource Request
  -> HAR Request
  -> NetLog URL_REQUEST
  -> Socket / DNS / TCP / TLS
  -> Renderer Dispatch
  -> Main-thread Task
  -> Rendering / Frame / Interaction
```

### 11.4 校时与匹配合同

- Trace 单调时钟、HAR 墙上时间和 NetLog tick 域分别保留，不得在摄入时直接覆盖为一个时间戳。
- 校时结果记录 anchor 类型、offset、uncertainty、样本数量、冲突和有效范围；跨出有效范围后重新降级。
- 导航开始、请求 ID、脱敏 URL 键、方法、重定向序号和阶段特征分别作为证据，不允许只靠 URL + 最近时间匹配。
- Service Worker、缓存命中、预加载、重定向和同 URL 并发请求必须有正例、反例与冲突样本。
- `medium` 或 `low` 关联在 UI 中显示“候选关联”，且不得参与确定端到端耗时或主因升级。
- 用户移除来源或校时失效时，Evidence Graph 与依赖结论同步撤销，不保留孤立边。

## 12. 前端设计

### 12.1 信息架构

- 左侧：症状、候选原因、跨源关联和限制，按当前选择范围过滤；不是全局告警堆叠区。
- 顶部：来源与会话状态、导航上下文、搜索、轨道配置、缩放历史、安全导出。
- 中部：概览、截图胶片、Brush 选区和多轨时间轴。
- 底部：Summary、Call Tree、Bottom-up、Event Log、Evidence Graph。
- 现有结论、网络、主线程、渲染和交互列表保留为聚合入口，逐步与选区共享状态。

工作台的单一页面任务是：在一个稳定时间范围内，把“症状 -> 候选原因 -> 时间事件 -> 原始证据”连成可往返的路径。视觉签名采用“证据游标”：同一个选区游标贯穿概览、胶片、各轨道、诊断和底部详情，所有联动均围绕它发生。其余界面保持克制，不使用玻璃拟态、远程字体、持续发光、科幻 HUD 或装饰性动画。

层级约束：

- 当前时间范围、选区和选中实体始终可见，避免用户在多个抽屉间失去上下文。
- 结论等级与证据质量使用文字和图形同时表达，不用红绿颜色代替语义。
- 一屏只突出一个主操作；默认是“检查当前选区”，导出、来源管理和轨道设置降为次级操作。
- 数值使用等宽或 tabular figures；正文不小于 13px，关键交互文字不小于 14px。

### 12.2 渲染技术

- Canvas 2D 绘制大量时间轴事件和关系线。
- DOM 绘制工具栏、轨道标题、设置、详情和无障碍替代内容。
- 首版不使用 WebGL；只有 Canvas 无法满足性能门禁时才升级。
- Event Log、Evidence 和 Network 列表使用虚拟化。

### 12.3 状态

高频状态放入独立 Timeline Store：

- 可见时间范围。
- 垂直滚动位置。
- 选区。
- 悬浮事件。
- 选中事件。
- 固定和隐藏轨道。
- 高亮实体及关系。

React 只订阅必要切片，避免缩放和平移触发整页重渲染。是否使用 `useSyncExternalStore` 由阶段 0 原型和 profiler 结果决定；Hook 选择本身不能作为性能门禁证据。

状态拥有者必须唯一：Worker 拥有会话数据和查询生命周期，Timeline Store 拥有高频交互状态，React 页面状态拥有抽屉、菜单和可访问性文本。时间范围、选区或选中事件不得在三处各自维护副本。

### 12.4 组件边界

| 组件 | 职责 |
|---|---|
| `TimelineViewport` | 时间换算、缩放、平移、选区、命中测试 |
| `TrackRegistry` | 轨道注册、排序、固定、隐藏和折叠 |
| `CanvasTrackRenderer` | 绘制事件、标记、关系和高亮 |
| `TimelineInteractionStore` | 高频交互状态和选择状态 |
| `AnalysisDrawer` | Summary、聚合视图、事件日志和证据图 |
| `InsightNavigator` | 诊断到时间范围、事件和跨源实体的导航 |
| `TraceWorkerQueryClient` | Worker 查询、取消、超时和错误处理 |
| `CrossSourceEvidenceGraph` | 跨源实体和证据路径展示 |

### 12.5 可访问性

- 核心工具栏和详情支持键盘操作。
- Canvas 选中事件提供等价 DOM 文本详情。
- 严重程度不能只依赖颜色，需搭配图标、纹理或文字。
- 支持 reduced motion。
- 提供“跳到时间轴”“跳到当前详情”的 skip link；焦点顺序与视觉顺序一致。
- 时间轴键盘路径至少支持：左右移动事件、Shift 扩展选区、Enter 打开详情、Escape 返回上一级选择；快捷键不得覆盖浏览器和辅助技术保留键。
- Canvas 不创建成百上千个隐藏可聚焦节点；当前可见轨道提供摘要，选中项和邻近项通过可虚拟化 DOM 列表访问。
- 桌面端优先，1280px 为基准验收宽度。1024–1279px 收起左侧面板并保留完整时间轴；低于 1024px 提供可读的结论与事件列表降级，不强塞完整工作台，也不产生页面级横向滚动。

### 12.6 时间轴交互契约

- 滚轮默认纵向滚动；`Ctrl/Cmd + 滚轮` 或显式控制缩放，避免劫持浏览器习惯。拖动画布平移必须有键盘和按钮替代。
- Brush 选区与单事件选择是不同状态。单击事件不应悄悄改写用户已有选区；需要时提供“将选区缩放到此事件”。
- 点击诊断时先保存当前视口历史，再聚焦关联时间范围并选中实体；返回操作恢复前一视口、选区、抽屉和滚动位置。
- 悬浮只提供预览，不触发 Worker 重聚合或永久状态改变；键盘聚焦和点击可获得同等信息。
- 查询超过 300ms 时保留旧画面并在受影响区域显示“正在更新当前范围”；不得清空 Canvas 后显示全屏 spinner。
- 搜索结果显示总数、当前序号、范围和截断状态；命中项必须可以前后导航并在轨道与 Event Log 中双向定位。

### 12.7 页面状态矩阵

| 状态 | 主界面 | 用户动作 | 禁止行为 |
|---|---|---|---|
| `indexing-minimum` | 现有诊断结果 + 真实索引进度 | 取消、返回结果 | 空白 Timeline、虚假 ETA |
| `ready` | 时间轴与当前选择详情 | 查询、缩放、选区、跳转 | 自动改变用户选区 |
| `enriching` | 稳定时间轴 + 局部任务状态 | 继续分析其他轨道 | 阻塞整个工作台 |
| `degraded` | 可用轨道 + 明确缺失原因 | 重试局部能力、查看限制 | 用空轨伪装无事件 |
| `empty-range` | 时间网格 + “当前范围没有匹配事件” | 清除筛选、返回全局 | 空白画布 |
| `query-error` | 保留旧画面 + 局部错误 | 重试、缩小范围 | 清空稳定结果 |
| `fatal-worker-error` | 现有报告结果 + 会话失败说明 | 重新建立会话、重新上传 | 自动主线程回退解析 |
| `released` | 文件已关闭说明 | 重新选择文件 | 继续使用旧响应 |

所有异步状态必须有可见反馈、明确恢复路径和 `aria-live` 文案。不可度量任务使用不定进度；只有真实单位可用时才显示数值进度。

### 12.8 视觉与主题约束

- 延续现有产品的本地证据控制台语义，使用项目本地字体栈和语义 token；不得引入远程字体。
- V5 亮色基准 token：Canvas `#EDF2F7`、Surface `#FFFFFF`、Ink `#152033`、Muted `#5F6F85`、Action `#1D5FC1`、Evidence `#6552A3`。错误、警告和成功继续映射项目语义 token，不在组件内新增任意 hex。
- 标题和正文使用系统无衬线字体栈；时间、ID、计数和阶段标签使用 `ui-monospace`。不为“品牌感”引入与本地离线工具不相称的展示字体。
- 数据轨道使用稳定的类别颜色，并辅以标签、形状或纹理。错误红、警告橙、选择蓝和证据紫只承担固定语义。
- 亮色与暗色主题分别验收文本 4.5:1、非文本图形 3:1、焦点环和 Canvas 选中态；不得用简单反色推导暗色主题。
- 动效只用于选区、抽屉和视口历史的空间连续性，150–250ms，可中断并遵守 reduced motion。
- 工具按钮点击区域不小于 40×40px；虽然桌面优先，关键操作仍按 44px 目标设计。

## 13. 分阶段落地

阶段不绑定日期和人力，以能力门禁决定是否进入下一阶段。

未经 Spike 和基准验证，不对 Canvas 时间轴、百万事件索引、CPU Profile 重建、竞争归因和跨源校准给出人日承诺。

当前建议状态：**阶段 0 进行中**。可靠接入和 Trace 报告页属于前置资产，不等于阶段 0 已完成；在合流 ref、引擎决策、协议评审和浏览器 benchmark 语料均有证据前，不得把路线图切换为“阶段 1 已完成”或直接开始完整 Timeline。

## 14. 质量门禁

### 14.1 正确性

- 时间戳、持续时间和时间域不得倒置。
- 父子关系、发起关系和调用栈必须稳定。
- self time 和 total time 与参考实现或人工基线一致。
- 证据 ID 不得悬空。
- 同一输入的结论和排序必须确定。
- 旧 `taskId`、旧 `sessionId` 或旧 `sessionRevision` 的响应不得改变当前界面。
- 100% 只在稳定结果已提交时出现；会话建索引必须作为独立任务呈现。
- 视口查询包含所有与范围相交的事件，包括从范围外开始的长事件。

### 14.2 诊断

- 因果结论至少包含一个必要证据。
- 证据缺失时降级为观察或禁用。
- 同时评估竞争原因和反证。
- 区分确定、高度相关、可能贡献、观察和证据不足。
- 每条主结论必须包含可执行的验证方法。

### 14.3 性能

- 缩放和平移 P95 ≤ 50ms。
- 悬浮反馈 P95 ≤ 100ms。
- 选区聚合 P95 ≤ 300ms。
- 取消响应 ≤ 500ms。
- 阶段基准回归不得超过 10%。
- 高频视口变化不产生无上限 Worker 请求队列；过期查询可观测地取消或丢弃。
- 性能报告同时保存源字节、解压字节、事件数、截图解码内存、传输量和峰值内存。

### 14.4 隐私

- URL 参数、Header、Cookie、Token、扩展 ID、截图和本地路径不得进入诊断或默认导出。
- 导出继续使用白名单 DTO。
- 原始截图只存在于分析会话内存。
- 敏感泄漏检测为零。

### 14.5 可维护性

- 引擎、数据模型、查询和渲染通过稳定接口隔离。
- 新增事件类型不修改通用时间轴交互逻辑。
- 新增轨道不修改核心画布。
- 规则、阈值和文案模板版本化。

### 14.6 体验与可访问性

- 键盘能够完成范围移动、事件选择、详情打开、返回和核心工具栏操作。
- Canvas 的当前选择、邻近事件和轨道摘要有等价 DOM 表达；屏幕阅读器不需要遍历全部事件节点。
- 亮色、暗色、200% 缩放、reduced motion 和 1280px/1024px 断点通过验收。
- 空态、局部加载、局部失败、截断和能力缺失均提供原因与下一步，不以空白区域表达状态。

十七个合成诊断场景主要证明规则与事实边界，不等于完整文件摄入、Worker 会话、Timeline 查询和 UI 已覆盖。测试报告必须把规则级 corpus、解析 fixture、协议契约、浏览器任务和仓库外真实样本分栏统计，禁止合并为一个“样本数”。

- ProfileChunk 尾部不完整和负时间差。

- LCP 发现晚、TTFB 高、主线程派发等待。
- 扩展存在但无影响的反例。

- CPU 受限与单一重任务的对照。
- GC 压力和无 GC 影响的对照。

### 15.7 CI 分层

- 新建独立 PR 校验工作流，不把所有测试和 benchmark 直接塞入部署工作流。
- 每次 PR 运行类型检查或生产构建、单元测试、契约测试、隐私扫描和小规模性能 smoke。
- 定时或手动运行 50 万、100 万事件 benchmark、仓库外真实样本和完整视觉回归。
- 部署工作流只依赖已经通过的质量结果或运行必要的发布前 smoke，不重复执行不稳定的大型性能任务。
- 性能门禁比较固定基准环境中的历史证据；共享 Runner 的单次绝对耗时只作为观察，不直接阻断发布。

## 16. 错误与降级

- 不支持的 Trace 形状：明确错误，不回退主线程解析。
- 缺少截图：隐藏胶片轨道并说明文件未包含截图。
- 缺少 CPU Profile：保留顶层任务，不虚构函数调用栈。
- 缺少导航或线程元数据：降级为全局轨道并禁用依赖能力。
- 时间未校准：来源轨道可独立展示，但不输出跨源端到端耗时。
- 事实或证据截断：在工作台显著展示，不静默继续。
- Worker 失败：释放 Blob URL、TypedArray 和会话资源。
- 查询超时或取消：保留当前稳定视图，不提交部分结果。
- 单轨查询失败：只在该轨道显示原因和重试，其他轨道与当前选区保持稳定。
- 截图解码失败：隐藏失败帧并显示计数，不阻断 Timeline 与诊断。
- 会话已经释放：丢弃迟到响应，显示“文件已关闭”，不自动重新读取本地文件。
- 建索引失败但基础报告可用：返回现有 Trace 结果页，并提供重新建立工作台会话的操作。

## 17. 风险与控制

| 风险 | 控制 |
|---|---|
| 第三方 Trace Engine API 不稳定 | 适配层、固定版本、Spike 和契约测试 |
| CRA 5 与 Worker/现代依赖兼容问题 | 阶段 0 验证；不同时迁移构建系统 |
| Canvas 可访问性不足 | DOM 工具栏、等价文本详情和键盘操作 |
| 百万事件内存膨胀 | 列式存储、字符串表、LOD、按需查询 |
| 截图泄漏或内存占用 | 会话内存、限制、去重、Blob URL 回收 |
| 归因误报 | 症状实体、必要证据、反证、竞争原因评估、Golden Corpus |
| 跨源错配 | 置信度、冲突展示、弱关联禁止确定结论 |
| 范围不断扩大 | 65% 门槛、阶段门禁、排除项和候选能力清单 |
| 解析报告与 Workbench 状态互相污染 | 分离 DTO、唯一状态拥有者、稳定 ID 和会话 revision |
| 高频视口查询堆积 | latest-wins、局部取消、背压上限和迟到响应丢弃 |
| feature flag 移除过早 | 每阶段保留报告页回退，发布门禁通过后再单独决策 |

## 18. 后续增强取舍

- 键盘导航属于核心可访问性能力，纳入 65% 阶段。
- 双 Trace 对比保留到 85% 阶段。
- Timeline 片段导出暂缓，必须先解决片段完整性、上下文依赖和隐私边界。
- 用户自定义诊断阈值暂缓，避免破坏规则结果的可重复性和发布门禁。
- 不生成携带分析数据的公开分享链接；优先使用本地脱敏文件导出。
- Perfetto 格式兼容只进入阶段 0 调研，不在 Spike 结论前承诺实现。

### 18.1 发布与回滚

- Workbench 使用独立 feature flag，与 Trace 文件接入 flag 分开控制；关闭 Workbench 时继续进入现有 Trace 报告页。
- 阶段 1 只对开发或内部样本开放，阶段 2 完成浏览器任务与隐私门禁后再逐步扩大。
- 回滚不得改变已确认的 parser 绑定、白名单导出和报告页诊断语义。
- 产品默认不上传遥测、文件指纹、URL、截图或原始性能数据。需要排查时由用户主动导出本地脱敏证据包。

## 19. 最终产品定义

项目的目标不是成为缩小版 DevTools，而是：

> 具备 Chrome Performance 核心离线分析能力、Perfetto 级时间轴与查询思想、Firefox/Speedscope 的 CPU 分析效率，并通过 Trace、HAR、NetLog 跨源证据形成可解释诊断的本地性能工作台。

核心 65% 完成后，用户应能在一个工作台中完成从问题发现、时间定位、调用栈或请求阶段分析，到证据确认和复测建议的闭环。长期 85% 在不改变这一核心闭环的前提下扩展高级离线能力。

### 19.1 普通用户诊断归因契约

结论首屏服务普通用户和一线支持。用户不需要理解 Trace 事件名、CPU Profile、线程或证据 ID，也必须能回答：原因是否已经确认、会造成什么影响、下一步该做什么。技术支持和研发通过折叠依据复核同一诊断模型，不能维护另一套结论。

| 归因状态 | 模型条件 | 首屏允许表达 | 首屏禁止表达 |
|---|---|---|---|
| 已确认原因 | `attributionLevel=confirmed` 且提供非空 `cause` | 明确展示具体原因、影响和处理动作 | 只有标签，没有可读原因 |
| 需要验证 | `highly-correlated` 或 `possible-contributor` | 说明关联线索、证据缺口和验证步骤 | 使用“已导致”“根因”等确定措辞 |
| 无法确认原因 | `observation`、`insufficient`，或 confirmed 记录缺少 `cause` | 说明无法确认的原因、缺失信息和重新采集方法 | 标为已确认原因、高影响或支持证据 |

`TraceDiagnosis.confidence` 只描述“现象或事实是否可信”，不代表因果归因已经完成。严重度描述现象影响大小，`DiagnosisFinding.attributionLevel` 才描述原因是否确认，三者不能互相替代。只有 `attributionLevel=confirmed` 且具有可展示 `cause` 时，首屏才允许出现“已确认原因”，并必须同步展示该原因文本。

CPU 采样额外遵循以下边界：

- `(idle)`、`(program)`、`(root)`、`(garbage collector)` 等运行时元节点不是业务脚本，不得命名为“脚本采样热点”。
- 采样无法映射到可识别函数时，输出“未能定位具体脚本”，解释缺少的函数或脚本位置，并提供重新录制方法。
- 有可识别函数但没有 Source Map 时，只能定位到 bundle/函数记录，归因状态为“需要验证”。
- 只有具体脚本执行与用户影响存在直接、可校准证据时，才允许升级为“已确认原因”。

首屏固定使用“归因判断 / 这会带来什么影响 / 为什么可以或不能确认 / 下一步怎么做”的结构。`Profile`、`ProfileChunk`、规则 ID 和证据 ID 只进入折叠的开发者依据。每张卡必须提供至少一个下一步动作，并保留到相关事实和原始证据的导航。
